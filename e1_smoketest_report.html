Why this is still useful

The original runner tokenized the string returned by llama.cpp's /apply-template with add_special=false. That endpoint omits BOS because a later string-based completion normally adds it; E1 instead sent token IDs, so BOS was never restored. With add_special=true, all seven prompt-token sequences match merged Hugging Face. Five of seven raw completions then match byte-for-byte; the two longer reasoning responses diverge after 42 and 35 common tokens but fail the same strict requirements.

Original versus fine-tuned model

The original upstream model also failed all four strict integrity checks and was much more verbose: 221, 252, 825, and 446 tokens versus the corrected fine-tune's 88, 89, 286, and 12. On the three code prompts, the original generated 1,433, 1,748, and 3,072 tokens; the fine-tune generated 98, 84, and 117 including EOS. The fine-tune is not simply “broken”: it substantially improved coding concision, while conversation-state hallucination and reasoning leakage remain real weaknesses.

Fix before scaling

  1. Plain-Python prompt created. lfm-code-v1 now requests raw Python only, without Markdown fences, outside explanation, or reasoning tags. V0 remains unchanged; the next suite version will adopt V1 before rerunning E1.
  2. Add a derived solution extractor. Preserve raw_completion unchanged. Separately derive solution by handling one closed <think> section, one Python fence, or plain Python. Reject ambiguous/malformed output. Parsing Python is allowed here; executing it is not.
  3. Keep the new behavioral and BOS gates. They now make the command exit non-zero for exact-output, invented-state, length, format, or prompt-encoding failures.
  4. Build E2 as a separate scoring container. It should have no network or GPU, run non-root with strict CPU/RAM/PID/time limits, mount only EvalPlus assets and derived samples read-only, and expose only a results directory as writable. Never mount the model, repository, Docker socket, credentials, or home directory into the scorer.
  5. Run E2 only on these three development tasks. Inspect extraction and scorer output. Once stable, keep HumanEval/0, 17, and 119 out of the sealed headline set as your frozen contract requires.
  6. Keep the A/B baseline in the benchmark plan. The frozen upstream and merged Hugging Face checkpoints were compared successfully. A separate original upstream GGUF is still needed if the final A/B must use exactly the same llama.cpp runtime.
